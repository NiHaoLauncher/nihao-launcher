# Minecraft Modpack Format

Status: **both sides are implemented.** Client: manifest generation/save/load/diffing (`plugin-sources/games/minecraft/src/library/modpack_format.rs`), export/import, and the calls to the server (`library/online_modpacks.rs`). Server: the routes under "Modpacks" / "Modpack content" in [`../../server/API.md`](../../server/API.md) (Minecraft's own server, not the launcher's general one). Below, `API.md` always means that file; it is the current wire contract.

## Why a custom format

The launcher needs to let a server publish updates to a modpack (add/remove/update mods, configs, resourcepacks, ...) and have the client download **only what actually changed** — not re-fetch the whole pack on every release. That means both sides need an addressable, comparable list of every file in the pack plus a way to tell "did this file change" without downloading it first. Hence: a flat manifest of `{path, sha256, size}` per file, versioned by a monotonically increasing build number.

This is deliberately close in shape to Modrinth's `modrinth.index.json` (a files array with hashes) and to how Mojang's own asset index works (content-addressed by hash) — both already-proven ideas for exactly this problem, just reshaped to fit this project's `.nihao`-file convention and to support server-authored diffing instead of only client-side import.

(The exported/imported archive itself is a plain `.zip` — see "Own format" below; `.nihao` here refers only to the per-instance `profile.nihao` file this section is about.)

## Where it lives: the `pack` field on `profile.nihao`

There's no separate manifest file. `profile.nihao` (`library/profile.rs`'s `MinecraftProfile`) was already "the file that describes this instance" — it just didn't yet track *which published pack, at which build* an instance came from. Rather than keep a second `.nihao` file in sync with it, the manifest below is simply the `pack` field on the existing struct:

```rust
pub struct MinecraftProfile {
    pub display_name: String,
    pub version_id: String,
    pub core: MinecraftLoader,
    pub loader_version: Option<String>,
    pub max_ram: u32,
    // ...RAM/java/icon fields, all local-only, unrelated to this doc...
    pub pack: Option<ModpackManifest>,   // <- this doc, in full
}
```

```
{game path}/instances/{instance-name}/
  profile.nihao     <- MinecraftProfile as a whole: player's local settings AND, in `pack`, this format
  mods/...
  config/...
  resourcepacks/...
  ...
```

`pack` is `None` for a from-scratch/custom instance that was never generated/imported as a tracked pack. Once set, it's this doc's `ModpackManifest` shape, serialized as part of the same JSON object — not a nested/stringified sub-document. Shown standalone below for clarity (and because this exact shape is also the server's wire format — see `API.md`, "Modpack content"):

```json
{
  "format_version": 1,
  "id": "cool-pack",
  "name": "Cool Pack",
  "build": 14,
  "version": "1.4.2",
  "minecraft_version": "1.20.1",
  "loader": "FABRIC",
  "loader_version": "0.15.11",
  "files": [
    {
      "path": "mods/sodium-fabric-0.5.3.jar",
      "sha256": "9f2c...e1",
      "size": 1234567,
      "source": { "type": "server" }
    },
    {
      "path": "config/sodium-options.json",
      "sha256": "a01b...44",
      "size": 512,
      "source": { "type": "server" }
    }
  ]
}
```

### Fields

| Field | Type | Notes |
|---|---|---|
| `format_version` | number | Currently always `1`. Bump on any breaking change to this shape. |
| `id` | string | Stable id of the pack **on the server** — not the local instance's folder name, which the player can rename freely and which has no bearing on this. This is the key a server would use to look up "the latest build of pack X". |
| `name` | string | Display name of the pack. |
| `build` | number (u64) | **The** version identifier — monotonically increasing, one per published release. Diffing and "is there an update" checks compare this, never `version`. A free-text version string is easy to reuse/skip/typo by a pack author; a counter isn't. |
| `version` | string, optional | Human-readable label only (e.g. `"1.4.2"`), shown to the player. Never compared programmatically — a server can put anything here. |
| `minecraft_version` | string | e.g. `"1.20.1"`. |
| `loader` | string | One of `"VANILLA"`, `"FABRIC"`, `"FORGE"`, `"NEOFORGE"` — matches `MinecraftLoader`'s Rust serialization exactly (uppercase, no `#[serde(rename)]` applied). |
| `loader_version` | string, optional | The loader's own build/version, when the loader needs one (Fabric, NeoForge). `null`/absent for vanilla. |
| `files` | array | Every distributable file in the pack. Sorted by `path` when generated by the client (not required by the format, just how this client's generator emits it). |

### File entry fields

| Field | Type | Notes |
|---|---|---|
| `path` | string | Instance-relative, **forward-slash-separated even on Windows**, so manifests compare byte-for-byte regardless of the OS that generated them. E.g. `"mods/sodium.jar"`, `"config/sodium-options.json"`. |
| `sha256` | string | Lowercase hex, 64 characters. Content hash of the file — this is what diffing compares. |
| `size` | number (u64) | Byte size. Not used for comparison (that's `sha256`'s job) — useful for progress bars and sanity-checking a download before trusting it. |
| `source` | object | Where to fetch this file's bytes from when it's missing or outdated. See below. |

### `source`

Internally tagged on `"type"`, so a server can mix delivery strategies file-by-file within one manifest:

```json
{ "type": "server" }
```
The `games/minecraft` server fragment itself serves the bytes (`GET /minecraft/modpacks/{id}/files/{path}`, see `API.md`). This is the default — `source` may be omitted entirely on a file entry and the client treats it as `"server"`.

```json
{ "type": "url", "url": "https://cdn.example.com/mods/sodium-fabric-0.5.3.jar" }
```
Fetch directly from an external URL (a CDN, Modrinth/CurseForge mirror, S3 bucket, ...) instead of proxying through the server. Exists so a large pack doesn't have to make the game server itself the bandwidth bottleneck for every mod jar — a server can publish a manifest that points most files straight at their original CDN and only self-host the handful of files it actually customized (configs, a modified resourcepack, ...).

### What's excluded from a generated manifest

The client's manifest generator (`generate_manifest` in `modpack_format.rs`) walks the instance directory and hashes everything **except**:

- Top-level `saves/`, `logs/`, `crash-reports/`, `screenshots/` — player/run-specific data. A pack update should never delete a player's world because it "isn't in the manifest."
- Any `*.nihao` file (`profile.nihao` itself) — local bookkeeping, not pack content. Notably, this also keeps a manifest from ever needing to describe itself.
- Any `icon.*` file — the player's own per-instance icon, not pack content.

If a server-side pack builder walks a *source* directory to build a manifest for publishing, it should apply the same exclusions (or its own equivalent) so it doesn't accidentally try to ship someone's `logs/latest.log`.

## Diffing

Given a local manifest (or none, for a from-scratch instance) and a remote one, the diff is:

- **`to_download`**: every file in the remote manifest whose `path` either doesn't exist locally, or exists with a different `sha256`. Carries the full file entry (so the caller has `sha256`/`size`/`source` to fetch and verify it).
- **`to_delete`**: every local file whose `path` isn't in the remote manifest at all — the pack dropped it, so a leftover mod jar the pack no longer includes should be removed too, not left behind as an orphan that might still load.

Files whose `path` and `sha256` are unchanged are simply not mentioned in the diff — nothing to do.

This is a **file-level** diff, not a byte-level/binary patch (no bsdiff, no rsync-style rolling hash) — deliberate: most changed files in a modpack update are mod jars, which are already-compressed zip archives where binary diffing buys little and costs a lot of complexity. Whole-file replacement is simpler, and downloading a changed jar is not meaningfully more expensive than downloading a patch for one plus decoding it.

## Client-side implementation (done)

`plugin-sources/games/minecraft/src/library/modpack_format.rs`:

- `ModpackManifest`, `ModpackFileEntry`, `FileSource` — the types above, `serde`-(de)serializable, matching this doc's JSON exactly.
- `generate_manifest(...)` — walks an instance directory, hashes every included file (SHA-256, streamed — doesn't load whole files into memory), and returns a fresh `ModpackManifest`. Runs on a blocking thread pool internally (`tokio::task::spawn_blocking`) since hashing is CPU/IO-bound. Doesn't save anything itself — the caller decides where the result goes.
- `diff_manifests(local: Option<&ModpackManifest>, remote: &ModpackManifest) -> ModpackDiff` — pure, synchronous, no I/O.

Saving/loading is just `MinecraftProfile::save`/`load` (`library/profile.rs`) — `pack` is a plain field on it now, nothing manifest-specific to call.

Exposed to the frontend as plugin-service calls (`interface.rs`, callable via `call_module("minecraft", <method>, args)` the same way every other Minecraft command already is):

- **`generate_modpack_manifest(path, name, id, pack_name, build, version)`** — scans the named instance, builds a manifest (pulling `minecraft_version`/`loader`/`loader_version` from the instance's existing profile rather than requiring them to be passed in redundantly), sets it as that instance's `profile.pack`, saves the profile, and returns the manifest. This is the "publish my instance as a pack" / "refresh the manifest after applying updates" action.
- **`get_modpack_manifest(path, name)`** — returns the instance's currently tracked manifest (`profile.pack`), or `null` if it doesn't have one.
- **`diff_modpack_manifest(path, name, remote)`** — takes a remote manifest (as JSON — fetched by the frontend from wherever the server API ends up living, not fetched here) and returns the diff against the instance's tracked manifest.

None of these three make a network call. Installing a published pack (fetching its manifest and every file) is `install_online_modpack` in `interface.rs`; applying a diff to an already-installed instance is not wired up — see "Not yet implemented" at the end.

## Share export (done) — for sharing a pack directly, without a server

`generate_modpack_manifest`'s manifest is deliberately lightweight (hashes only) because it assumes a server hosts the actual bytes — and even then a player may want to just hand a pack to a friend directly. The "Share" button (`ActionsBanner` → `ShareModal`, `plugin-sources/games/minecraft/ui/src/pages/share.tsx`) exports the current instance as one self-contained zip a receiver can use with **no server or NiHaoLauncher account involved**. Implemented in `library/export.rs`, exposed as `export_modpack_own(path, name, include, dest_path)` and `export_modpack_mrpack(path, name, include, dest_path)`; the frontend picks `dest_path` via a native save dialog before calling either.

`include` is the set of top-level folder/file names to actually export — the Share modal shows a checklist of every entry `list_export_entries(path, name)` returns (everything directly inside the instance dir, minus `profile.nihao`/`icon`/`banner` — those are never a choice), pre-checking `config`, `mods`, `datapacks`, `resourcepacks`, and `shaderpacks` by default. Both export functions filter to files whose top-level component is in `include` (`export::filter_by_top_level`) rather than relying on `generate_manifest`'s fixed `saves`/`logs`/`crash-reports`/`screenshots` blacklist — sharing is an explicit per-file choice here, so even those can be included if the player checks them.

Both `export_modpack_*` commands run the same way `create_modpack` does — kicked off on a background thread, returning immediately (`{"status": "exporting"}`) rather than blocking the FFI call until the whole zip is written. Progress (hashing → Modrinth lookup, for `.mrpack` → writing the archive) is reported through `library::export::ProgressCallback` into the same `install_state()` the launcher's bottom `.progress` bar already polls via `get_install_status`, tracked under the key `"{instance name} (export)"` (`export_job_label` in `interface.rs`) — so an export shows progress there with no dedicated UI of its own, and the Share modal just polls the same endpoint (`waitForBackgroundJob` in `pages/helpers.ts`) for that entry to disappear to know it's done (checking `lastError` for that same label to tell success from failure).

### Own format (`export_modpack_own`)

```
<chosen-file>.zip
  manifest.json      <- ModpackManifest, exactly this doc's shape
  files/...           <- every file the manifest lists, actual bytes, same relative paths
```

(Was `.nihaopack` — switched to a plain `.zip` extension since the file is a standard zip archive either way; nothing about detection depends on the extension, `peek`/`import` read `manifest.json` from inside it regardless of what it's named.)

Unlike the `pack` field's manifest, `source` on every entry is meaningless here (there's no server) — it's left at the default `{"type": "server"}` purely because reusing `ModpackManifest` as-is means one less type to maintain. A receiver's launcher (this one, once import is built — see below) just unzips `files/` straight into a new instance directory and trusts `manifest.json` for display info.

`id`/`name`/`build`/`version` come from the instance's tracked `pack` if it has one (i.e. `generate_modpack_manifest` was run before), otherwise default to the instance's folder name / display name / build `1` / no version — exporting has never required publishing first.

### Modrinth format (`export_modpack_mrpack`)

A standard `.mrpack` (the format Modrinth itself, Prism Launcher, ATLauncher, etc. all read):

```
<chosen-file>.mrpack  (a zip)
  modrinth.index.json
  overrides/...        <- files Modrinth didn't recognize
```

Every file is hashed with SHA-1 and checked against Modrinth's `POST /version_files` (`{"hashes": [...], "algorithm": "sha1"}`, batched `HASH_LOOKUP_CHUNK` — 200 — hashes per request). A match contributes a `files[]` entry pointing at Modrinth's own CDN (`downloads`, `hashes.sha1`/`hashes.sha512`, `fileSize` — all taken from Modrinth's response, not recomputed locally); everything unmatched (configs, resourcepacks not on Modrinth, local-only files) is bundled under `overrides/` instead, so the export is always complete and installable even fully offline (the lookup call is best-effort — a failed/unreachable request just means every file falls back to `overrides/`, never a hard error). `env` on matched files is always `{"client": "required", "server": "required"}` — resolving real per-project client/server support would mean an extra API call per project, not done here. `dependencies` maps `minecraft_version` and, for non-vanilla instances, the loader (`fabric-loader`/`forge`/`neoforge`) to its version.

## Publish to NiHao (done) — modpack.nihao, for uploading to the real server

A third export shape, alongside "Own format" and Modrinth above — but unlike those two, this one
*does* involve a server: it's the zip `POST /minecraft/modpacks/{id}/builds` (API.md) actually
receives when a player uses Share → "Publish to NiHao". Same Modrinth-resolution idea as
`.mrpack`, but the manifest is its own shape (`PublishManifest` in `library/export.rs`) — not
the `pack`-field `ModpackManifest` this doc opens with, and not `modrinth.index.json` — under the
reserved filename `modpack.nihao`, kept distinct from `manifest.json` (own format) and
`modrinth.index.json` (mrpack) so whatever reads a zip back can tell which of the three shapes
it's looking at from the manifest filename alone, no format-sniffing needed:

```
<uploaded>.zip
  modpack.nihao      <- PublishManifest, see below
  override/...        <- files Modrinth didn't recognize, actual bytes, same relative paths —
                          unpacked straight into the modpack's own root once installed, e.g.
                          override/mods/x.jar lands at mods/x.jar, not override/mods/x.jar
```

`modpack.nihao` is deliberately *not* the full `ModpackManifest` shape from earlier in this doc —
`format_version`, `id`, `name`, and `build` are all dropped. `id`/`name` already exist on the
`Modpacks` row from registration (the URL's `{id}` says which pack this build is for — no reason
to repeat it in the body), and `build` is decided server-side (`Modpacks.latest_build + 1`) —
none of the three would do anything but get ignored if sent:

```json
{
  "version": "1.4.2",
  "minecraft_version": "1.20.1",
  "loader": "fabric",
  "loader_version": "0.15.11",
  "files": [
    {
      "path": "mods/sodium-fabric-0.5.3.jar",
      "sha256": "9f2c...e1",
      "size": 1234567,
      "source": { "type": "url", "url": "https://cdn.modrinth.com/data/.../sodium-fabric-0.5.3.jar" }
    },
    {
      "path": "config/sodium-options.json",
      "sha256": "a01b...44",
      "size": 512,
      "source": { "type": "server" }
    }
  ]
}
```

`loader` accepts any case here (server normalizes to uppercase to match `ModpackManifest`'s own
enum, same convention the old multipart `loader` field used before this shape existed) — the
client's own `PublishManifest` sends whatever `MinecraftLoader`'s Rust serialization produces
(uppercase), which is well within "any case." `version`/`loader_version` are omitted entirely
(not `null`) when unset, same as everywhere else in this project's JSON. For a `"server"`-sourced
entry, whatever `sha256`/`size` the client puts here is ignored and recomputed from the actual
bytes at `override/<path>` — the server only trusts what it can check itself.

Same hash-and-lookup pass as the `.mrpack` export (SHA-1 against Modrinth's `POST
/version_files`, `HASH_LOOKUP_CHUNK`-batched) — but every included file, matched or not, gets a
real entry in `files[]` (`sha256` always computed locally from the file on disk, regardless of
whether Modrinth also recognized it):

- **Matched** (Modrinth has it): `source: { "type": "url", "url": "<Modrinth CDN URL>" }`. Its
  bytes are never written into the zip at all — whoever later installs this build fetches the
  file straight from Modrinth, the same `source.type == "url"` handling this doc already
  specifies above. This is the whole point: a pack whose mods mostly come from Modrinth (the
  common case) uploads a small zip instead of re-uploading gigabytes of jars NiHao's own server
  would just be mirroring.
- **Unmatched**: `source: { "type": "server" }`, and the actual bytes go into the zip at
  `override/<path>` (the manifest entry's own `path`, just prefixed) — this is what the server
  actually stores on its own disk and serves back from `.../files/{path}` for this build.

`icon`/`banner`, for visualizing the pack, currently still ride along on the same
`POST .../builds` call as separate `multipart/form-data` fields (see API.md) rather than living
inside the zip — unchanged from before this format existed.

Implemented as `export_for_publish(instance_dir, id, name, version, minecraft_version, loader,
loader_version, include, dest_path, on_progress)` in `library/export.rs`, called from
`publish_modpack_build` (`interface.rs`) — the third Share option. Same background-job/progress
convention as every other export/import here (`install_state()`, tracked under
`export_job_label(name)`); the frontend polls it exactly like an own-format or `.mrpack` export.

On the *downloading* side, nothing extra was needed: `install_online_modpack`'s per-file fetch
already branches on `source.type` (`FileSource::Server` vs `FileSource::Url`) — a `url`-sourced
entry in a build's manifest is fetched straight from wherever it points, same as it always would
have been for any other reason a manifest might carry one.

## Import (done) — the reverse: a modpack file → a new instance

`library/import.rs`, exposed as `peek_modpack_file(source_path)` and `import_modpack(path, name, source_path, minecraft_version, loader, loader_version)`, driven by the "Create Modpack" modal's **Install modpack** card (`CreateModpackModal`, `plugin-sources/games/minecraft/ui/src/pages/createModpack.tsx`). `peek_modpack_file` looks for `manifest.json`/`modrinth.index.json` (whichever the file has) without extracting or downloading anything — fast enough to run the moment the player picks a file, to populate an editable name field and show the detected game version/loader before they commit.

A plain `.zip` with **neither** manifest — a mods/configs/resourcepacks folder someone zipped up by hand, not something this app or Modrinth produced — isn't rejected: `peek` returns `format: "raw"` with `minecraft_version`/`loader` left empty, and the confirm screen "unlocks" editable version/loader pickers (the same ones "Custom setup" uses) for the player to fill in instead. Those become `import_modpack`'s `minecraft_version`/`loader`/`loader_version` params, used only for this case.

`import_modpack` mirrors `create_modpack`'s own shape: it's a background job (`{"status": "installing", "name": ...}` returned immediately) reporting progress through the same `install_state()`/bottom `.progress` bar as everything else here, under the plain instance name (not the `"(export)"`-suffixed label export jobs use — an import genuinely *is* a create+install, so it reuses that exact convention). Two phases, back to back:

1. **Unpack the pack's own content** — `import_own_format` extracts `files/` per `manifest.json` (and, since the manifest round-trips exactly, sets the new instance's `profile.pack` to it, same as a fresh `generate_modpack_manifest`/export would); `import_mrpack` extracts `overrides/`/`client-overrides/` and downloads every `files[]` entry from its `downloads` URL; `import_raw_zip` (the `"raw"` case) just extracts every entry in the zip directly into the instance directory, no prefix or manifest involved.
2. **The normal install pipeline** — none of the three bundle the actual Minecraft client/libraries/assets/Java, only mods/configs/resourcepacks, so this step is *exactly* `create_modpack`'s own `instance.install_stream()` call, reusing `build_instance` and `InstallProgress::from_info` verbatim. (The progress bar's fraction visibly resets when this phase starts — deliberate simplification rather than unifying two independently-shaped progress schemes; not worth the complexity for what's a cosmetic-only hiccup.)

### Not yet implemented

- Resolving matched files' per-project `client`/`server` support from Modrinth instead of hardcoding `"required"` (export side).
- Detecting/handling a name collision with an existing instance on import — `import_modpack` just writes `profile.nihao` to `{path}/instances/{name}`, same permissive "re-using a name re-saves it" behavior `create_modpack` already has (see its own doc comment) — nothing prompts the player if that's not what they meant.

## Server-side storage: one file, and is that fast enough?

Yes to both — store each published build as one JSON file, e.g.:
```
data/modpacks/{id}/{build}.json
```
containing exactly the `ModpackManifest` shape above (`id`, `name`, `build`, `version`, `minecraft_version`, `loader`, `loader_version`, `files`). That's the whole storage model for the manifest itself — no database table needed just to hold it, since it's already a self-contained, immutable-once-published document (a given `{id}/{build}` never changes; a new release is a new `build` number, a new file).

Why this is fine even though `GET .../modpacks/{id}` and `.../manifest` will be the most frequently hit endpoints (every client checks on close to every launch, per API.md's own "meant to be opened once per launch" convention for the connection stream — this is the same usage shape): a manifest is small text — a pack with a couple hundred mod files is maybe tens of KB of JSON. Reading and parsing a file that size is sub-millisecond, and the OS page cache keeps a frequently-read small file like this in memory across requests automatically — you get "fast" for free without writing any caching code. `actix-web` handling thousands of small-file reads/second on ordinary disk is not a bottleneck at the scale this launcher operates at.

What *would* be worth adding once/if it ever actually matters (don't build this up front — it's speculative until a real load pattern says otherwise):
- An in-process cache (`Arc<RwLock<HashMap<(pack_id, build), ModpackManifest>>>`, or just always cache "latest") in front of the file read, invalidated on publish. Skips the disk read (and JSON parse) entirely for the hot path.
- Precomputing the "latest build" answer once per publish rather than re-listing `data/modpacks/{id}/*.json` on every `GET .../modpacks/{id}` call (a directory listing to find the max build number is still fast, but a cached pointer is faster and simpler than re-deriving it each time).

Two things that genuinely do need a real, non-file-per-request answer: the *file bytes* endpoint (`.../files/{path}`) if a pack's files are large or numerous — that's arguably better served by pointing `source` at a CDN/URL (see above) than by proxying gigabytes of mod jars through the same process serving JSON manifests — and whatever storage holds the actual uploaded files server-side (plain filesystem under `{id}/{build}/mods/sodium.jar` etc. works fine to start, mirroring the manifest's own `path` field 1:1, so no separate file-lookup index is needed there either).

### Not yet implemented

- Updating an already-installed pack in place. `diff_modpack_manifest` takes the remote manifest as an argument, but nothing fetches `GET .../manifest` or calls `POST .../diff` and then applies `to_download` / `to_delete` to an existing instance; `install_online_modpack` only creates a new instance.
